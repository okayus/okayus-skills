# Full workflow YAML template

Copy-ready `.github/workflows/backup.yml` for a Cloudflare Workers + D1 + pnpm monorepo. All known gotchas (Trap 1 / Trap 2 / path quirk / cron UTC) are addressed inline.

## Template

```yaml
name: D1 weekly backup

on:
  schedule:
    - cron: '0 3 * * 0'  # UTC Sun 03:00 = JST Sun 12:00. Adjust per your local TZ.
  workflow_dispatch:       # always include — needed for first-run + ad-hoc backups

concurrency:
  group: backup-${{ github.ref }}
  cancel-in-progress: false  # backups should not interrupt each other

jobs:
  backup:
    runs-on: ubuntu-latest
    permissions:
      contents: write       # to commit the backup file to a new branch
      pull-requests: write  # to open the PR
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 9.15.0
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
      - run: pnpm install --frozen-lockfile

      - name: Export D1 (remote) to backups/
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          CLOUDFLARE_ACCOUNT_ID: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
        run: |
          DATE=$(date -u +%Y%m%d)
          mkdir -p backups
          # backups/ is at the repo root. Inside `pnpm --filter`, cwd becomes
          # packages/<pkg>/, so the output path needs ../../backups/.
          pnpm --filter @<your-org>/<pkg> exec wrangler d1 export <your-db-name> \
            --remote --output ../../backups/backup-weekly-${DATE}.sql

      - name: Create PR
        uses: peter-evans/create-pull-request@v7
        with:
          commit-message: "chore(backup): weekly D1 export"
          title: "chore(backup): weekly D1 export"
          body: |
            Weekly D1 backup generated by `.github/workflows/backup.yml`.

            Review the diff (file size, table counts, no obvious data loss)
            before merging. This file is the recovery source if D1 data
            is lost or credentials are compromised.

            Restore: `wrangler d1 execute <db-name> --remote --file <this-file>`
          branch: chore/backup-${{ github.run_id }}
          labels: backup
          delete-branch: true
```

## Variables to fill in

| Placeholder | What to replace with | Where to find it |
|---|---|---|
| `@<your-org>/<pkg>` | Workspace package name | `package.json` `name:` field |
| `<your-db-name>` | D1 database name | `wrangler.jsonc` `d1_databases[0].database_name` |
| Cron schedule | Your timezone-converted UTC cron | See "cron schedule" section in main SKILL.md |
| pnpm version | Match the version your repo uses | `package.json` `packageManager:` field, or your `pnpm-workspace.yaml` |
| Node version | Match your repo standard | `.github/workflows/deploy.yml` for consistency |

## Why each piece exists

### `concurrency`

Prevents two backup runs from racing. Unlike a deploy workflow (where you might want to cancel-in-progress to avoid stale deploys), backups should complete sequentially — `cancel-in-progress: false`. If a manual `workflow_dispatch` overlaps with the cron, both finish in order.

### `permissions: contents: write` + `pull-requests: write`

Both required for `peter-evans/create-pull-request@v7`. See main SKILL.md "Trap 2".

### `mkdir -p backups`

Defensive. If `backups/` doesn't exist yet (fresh setup), `wrangler` will fail to write. The `-p` flag is a no-op if it already exists.

### `DATE=$(date -u +%Y%m%d)`

Format choice: `YYYYMMDD` for filename-safe sort order. `+%F` (= `YYYY-MM-DD`) is also fine. **Use UTC** (`-u` flag) so consecutive runs from different timezones don't produce confusingly close filenames.

### `peter-evans/create-pull-request@v7`

Mature action, ~3 years stable, used in many repos. Alternatives:
- `gh pr create` directly: works but more code, harder to handle the "no diff" case (e.g., if D1 hasn't changed since last backup, the action sensibly skips the PR)
- Manual git commands + `gh api`: more control, more failure modes

`peter-evans/create-pull-request@v7` skips the PR if the branch has no diff vs base, which is the right behavior for backups (don't open empty PRs).

### `delete-branch: true`

After merge, deletes the auto-created branch. Without this, you accumulate dozens of `chore/backup-<runid>` branches in the remote.

### `labels: backup`

Lets you filter backup PRs separately: `gh pr list --label backup`. Useful for quickly finding the latest one to review.

## Optional enhancements

### Notify Discord/Slack on backup completion

Add a step after the PR creation:

```yaml
      - name: Notify Discord
        if: success()
        env:
          WEBHOOK: ${{ secrets.DISCORD_WEBHOOK_URL }}
        run: |
          PR_URL=$(gh pr list --label backup --state open --limit 1 --json url --jq '.[0].url')
          curl -X POST -H 'Content-Type: application/json' \
            -d "{\"content\":\"Weekly D1 backup PR opened: ${PR_URL}\"}" \
            "${WEBHOOK}"
```

For a personal project this might be overkill. For a 2-3 person team, the ping is helpful so backup PRs get reviewed within a few days.

### Fail loudly if backup is suspiciously small

A zero-byte or sub-1-KB backup file usually means the export silently failed (D1 returned empty due to auth error, race condition, etc.):

```yaml
      - name: Sanity check backup size
        run: |
          SIZE=$(stat -c%s backups/backup-weekly-*.sql)
          if [ "$SIZE" -lt 1024 ]; then
            echo "Backup is suspiciously small (${SIZE} bytes). Failing."
            exit 1
          fi
```

This won't catch all corruption — a backup that's missing one table won't trip the size check — but it catches the common "export silently failed" failure mode.

### Compare row counts vs last week

More elaborate. Open the previous backup, count rows in each table, compare to current. Add a comment to the PR if any table dropped >10%. This is overkill for personal projects but worth knowing exists if you scale up.

## What to NOT add

- Encryption of the SQL file in the workflow: encryption-at-rest is the storage's job, not the workflow's. If you need encrypted backups, switch to R2 with KMS.
- Auto-merge of backup PRs: defeats the review-the-diff property that's the main reason to use PRs in the first place.
- Backup of `.dev.vars` or other secrets: secrets should be in your password manager / `wrangler secret put`, not in repo backups.

## Troubleshooting

| Error | Fix |
|---|---|
| `GitHub Actions is not permitted to create or approve pull requests` | Trap 1 — flip the repo setting |
| `Resource not accessible by integration` on git push or PR open | Missing `permissions:` block (Trap 2) |
| `Authentication error 7403` on `wrangler d1 export` | `CLOUDFLARE_API_TOKEN` missing `D1 : Edit` scope |
| `--output backups/...` produces file in `packages/<pkg>/backups/` | The `pnpm --filter` cwd quirk — use `../../backups/` |
| `mkdir: cannot create directory 'backups': File exists` | The `-p` flag is missing — add it |
| Cron fires but no PR appears | First-run trap (1) likely missed; or no diff vs base (= D1 hasn't changed); check workflow run logs |
| PR created but the SQL file is 0 bytes | Network blip or `wrangler` silent failure; re-run; if persistent, add the size sanity check |

When in doubt, `gh run view <id> --log` shows the full output of every step, including the wrangler export.
